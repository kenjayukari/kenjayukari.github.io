分库分表

  • QPS：Queries Per Second，系统每秒实际处理的查询请求数
  • TPS：Transactions Per Second，系统每秒完成的事务数（一个事务包含多个请求）
  • PV：Page View，页面浏览量
  • UV：Unique Visitor，独立访客数

为什么要分库分表？

[!question] 为什么要分库分表？

  • 查询性能随着数据量增长呈指数级增长
  • 什么情况分表：需要考虑业务的增长量和历史数量，主要解决单表数据量过大问题，数据量庞大或数据库表对应的磁盘文件过大
    • 查询速度慢：数据量过大，索引B+树的层级变高，会导致IO增加
    • 不利于运维：日常业务中需对磁盘每天备份，且遇到损伤时对恢复过程产生影响。
  • 什么情况分库（Sharding）：数据库承载的 QPS 越来越高，数据库连接不够，可考虑分库或读写分离
    • 场景：MySQL Server 最大支持 4000 个并发连接，假设后端微服务的订单服务部署了 40 个节点，每个节点连接池的最大容量设为 10 个，部署了 40 个节点（占用 400 个连接），如果类似这样的服务有 10 个，总连接数将达到 4000 个，此时 MySQL Server 的连接数就会耗尽，无法处理新请求
    • 注：连接不够用，应优先考虑读写分离
      • 读写分离：在物理上把一个库变成多个库（主库+从库），配多数据源。不涉及业务上的拆分，主要做主从同步
      • 局限性：读写分离一般足够应对读压力，但主从同步存在延迟，无法满足对数据一致性要求极高的业务场景（如支付、强事务场景）。当读写分离也无法缓解写压力或连接瓶颈时，才考虑分库
  • 什么情况分库分表：主要处理高并发写入、数据量巨大场景
  • 分库、分表都有两种模式：垂直分库、分表和水平分库、分表
    • 垂直分库：按业务拆分为多个数据库
    • 垂直分表：将不常用的信息放在用户扩展表，提升并发性能
    • 水平分库：将用户数据库拆分为多个
    • 水平分表：将用户表拆分为多个

ShardingSphere

  • Apache ShardingSphere：分布式数据库生态系统，将任意数据库转换为分布式数据库，包含以下两个产品
    1. ShardingSphere-JDBC：增强版 JDBC 驱动，客户端直连数据库
      • 导入 Jar 包来获取服务，无需额外部署和依赖，完全兼容 JDBC 和 ORM 框架
    2. ShardingSphere-Proxy：透明化的数据库代理端，通过实现数据库二进制协议，对异构语言提供支持
      • 无需对现有项目做任何配置或代码变更，将数据库的地址改为 Proxy 的地址
  • 混合部署：
    • 通过混合使用 ShardingSphere-JDBC 和 ShardingSphere-Proxy，并采用同一注册中心统一配置分片策略，能够灵活的搭建适用于各种场景的应用系统，使得架构师更加自由地调整适合于当前业务的最佳系统架构
      • ShardingSphere-JDBC 本地分片计算，路由结果后，与应用下方的底层数据库节点建立连接，并下发真实的 SQL 语句
      • ShardingSphere-Proxy 接收到客户端发来的标准 SQL 后，会在本进程内完成解析、路由、改写、执行和结果归并。然后代表客户端，向下方的真实数据库节点发起请求

分片键逻辑

  • 全表查询：无分片键，查询最慢
    • 局限性：基于哈希算法无法做范围/模糊查询，同样是全表查询
  • 分片键（Sharding Key）：用于将数据库(表)水平拆分的数据库字段，对表操作时，根据分片键通过分片算法路由到对应表，避免扫描所有分表，选择分片键的关键因素：
    1. 访问频率：将高频访问的数据放在同一个分片上，可提升查询性能和降低跨分片查询的开销
    2. 数据均匀性：分片键应保证数据均匀分布在各分片上，避免出现热点数据集中在某个分片上的情况
    3. 数据不可变：分片键一经创建不可修改，不能随着业务变化而频繁修改

      [!question] 数据库表中的用户名和用户ID选择哪个？

      • 提升查询效率：在用户登录操作中，系统频繁地通过用户名来查询用户信息，使用用户名可直接作为分片键路由到包含该用户名数据的特定数据库表/数据节点

绑定表与广播表

  • 绑定表：分片规则一致的一组分片表，使用绑定表进行多表关联查询必须用分片键关联，如 t_order 和 t_order_item 均按 order_id 分片，并使用 order_id 关联
    • 即 t_order_0 里的订单，对应的订单明细应该在 t_order_item_0

[!extension] 广播表（Broadcast Table）

  • 所有数据源下的数据库中都存在且完全相同的表。 适用于数据量不大且需要与海量数据的表进行关联查询的场景（避免跨库 JOIN），例如：字典表
  • 写操作：中间件 ShardingSphere 会在所有数据源上同时执行操作，确保数据一致性
  • 读操作：只需就近选择一个查找
  • 多表关联查询示例：假设分片键 order_id 将数值 10 路由至第 0 片，将数值 11 路由至第 1 片
  • 不配置绑定表关系：路由后的 SQL 为 4 条，呈现为笛卡尔积
  • 配置绑定表关系：使用 order_id 进行关联后，路由后的 SQL 为 2 条

行表达式

  • 简化数据节点配置工作量：通过行表达式书写分片算法，可有效将规则配置统一存放，易于浏览与存储
  • 行表达式作为字符串由两部分组成：<GROOVY>t_order_${1..3}
    1. 对应 SPI 实现的 Type Name 部分，如 <GROOVY>
    2. 表达式部分，如 t_order_${1..3}
    • 当行表达式不指定 Type Name 时，例如 t_order_${1..3}，行表示式默认将使用 InlineExpressionParser SPI 的 GROOVY 实现来解析表达式

      [!info] GROOVY 实现的语法规则

      • 省略 <GROOVY> 时，默认走 Groovy 解析器
      • 本质为 Groovy 脚本，可以写算术运算符
      • 范围${...} 或 $->{...}：如 t_order_${1..3} -> t_order_1, t_order_1, t_order_3
      • 枚举集合[v1, v2]：如 ${['online', 'offline']} -> 展开 online, offline
      • 笛卡尔组合：如 ${['online', 'offline']}_table${1..3}
